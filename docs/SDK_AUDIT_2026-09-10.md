## Audit loops

1. Inventory every SDK and its resource, transport, error, webhook and test modules. Run the existing suites before changing runtime behavior.
2. Trace changed API contracts: durable send identity, interrupted batches, reply/forward, tracking health, campaign/follow-up cancellation, contact upserts and permanent received-message deletion. Preserve HTML/text content as supplied; editor rendering remains server-owned.
3. Challenge failure boundaries with scripted responses and local HTTP servers: partial work, proxy errors, response-body failures, redirects, cancellation and malformed additive error fields.
4. Implement shared policy and per-language regressions; run all language suites/builds, CLI against the local Node build, and cross-language contract checks. Record compatibility and release requirements.

## Findings before implementation

| ID | Finding | Evidence / affected surface |
| --- | --- | --- |
| S01 | Automatic retries disregard terminal partial/uncertain results; unkeyed mutation retries also treat generic proxy 503s as proof nothing happened. | Seven language transports retry solely by status; Python guards sent counts but not reserved prefixes. Node reproduction makes two requests for partial and ambiguous outcomes. The current backend protects keyless partial sends with HTTP 422, but keyed partial responses still undergo useless retries and generic proxy outcomes remain ambiguous. |
| S02 | No SDK reply/forward method accepts the newly supported operation key. | All eight resource wrappers omit request options; CLI has no reply/forward key flags. Repeating an application-level reply after losing its response cannot use the server's new deduplication contract. |
| S03 | Default redirects can move authenticated API requests or private payloads to another destination. | Local Python 302 test forwards the fake Bearer header to a second server. Node 307 test forwards the email body. Go, .NET and Rust also construct clients with redirect-following defaults. PHP, Java and Ruby already refuse redirects. |
| S04 | Node response-body failures escape its documented `{data,error}` result contract. | A real failing ReadableStream rejects JSON/text/binary reads outside the transport catch; the new regression fails on the baseline. Retry responses also remain unread. |
| S05 | Python socket/read failures escape its SDK exception contract. | A direct TimeoutError is not a urllib URLError and escapes as TimeoutError; truncated reads have the same uncovered boundary. |
| S06 | Go ignores caller cancellation while waiting to retry. | The context-aware request loop calls unconditional `time.Sleep`, which can retain a canceled operation for the entire Retry-After delay. |
| S07 | Several error decoders trust an embedded status over the actual HTTP response. | Node's own comment says transport status wins but its implementation chooses body.statusCode; Python, Go, Ruby, PHP, .NET and Rust have analogous paths. A stale/malformed body can misclassify the actual result. |
| S08 | New recovery and tracking contracts are not discoverable in the SDK surface/docs. | Tracking-health has no resource method; errors lack typed access to the unconfirmed email ID/reserved prefix/never-attempted count; docs say only send/batch support idempotency and omit stopping follow-ups on sent campaigns. Raw additive error bodies are already retained and must stay compatible. |
| S09 | .NET serializes a mutable request object again on each retry. | A regression changes the caller’s options after the first 429. The second request sends the changed text under the original key. The before-fix test fails with two different serialized bodies; the fix snapshots JSON once before entering the retry loop. |

The first Node reproduction run had 10 failing and 7 passing regression cases. Python local-server evidence confirmed redirect credential forwarding and unwrapped timeout errors. Existing tests passed; those suites alone did not exercise these cases.

## Required retry contract

- Only HTTP 429/503 are candidates; network errors, body-read failures, 409, 422 and other 5xx responses are not automatically retried.
- Stop immediately if an error identifies an email, a sent count/list, a reserved prefix or a terminal incomplete batch. Preserve the body so callers can inspect confirmed, uncertain and never-attempted work separately.
- A generic 503 may be retried for a read, or a send endpoint protected by the same operation key. Other mutations require a documented pre-application rejection; an arbitrary idempotency header on an endpoint that ignores it supplies no protection.
- Keep the same serialized payload and key for every automatic attempt. Do not generate a new key on retry.
- Default transports do not follow redirects. Explicitly supplied custom transports remain the caller's responsibility where the language API gives them ownership of redirect policy.

## Research references

[RFC 9110 on automatic retries](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), [Python redirect handling](https://docs.python.org/3/library/urllib.request.html#urllib.request.HTTPRedirectHandler), [Go HTTP client behavior](https://pkg.go.dev/net/http#Client), and [.NET response completion](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption) informed the transport review. In particular, .NET's default SendAsync buffers the content under the existing cancellation token; its timeout boundary was reviewed and was not treated as the Node body-read defect.

Custom caller-owned clients retain their configured policy. |
| S04 | Node consumes every body under the attempt’s signal, inside the Result error boundary, including retry bodies. | Failing ReadableStreams and an actual HTTP server that sends headers but stalls the body exercise JSON, text and binary reads. They return network_error and do not retry. |
| S05 | Python wraps direct socket/read exceptions, including reads of HTTPError bodies; closes error responses. | TimeoutError and IncompleteRead regressions cover ordinary and error response paths; existing timeout and error tests remain green. |
| S06 | Go uses a context-aware timer for Retry-After; delay parsing handles nonfinite/overflowing values. | Cancellation during a 500 ms wait returns at the caller’s 30 ms deadline; complete Go suite passes with the race detector. |
| S07 | Actual HTTP status wins. .NET parses envelope fields independently so malformed status/name/message shapes cannot discard unrelated recovery metadata. | Every SDK tests a conflicting body status; the shared malformed-status case verifies progress still prevents a retry. |
| S08 | Tracking-health wrapper in eight SDKs and CLI; typed fields/accessors for original ID, reserved prefix and never-attempted count; all package READMEs updated. | Exact endpoint and response-shape tests, public type compilation, full existing resource suites, and CLI integration. |
| S09 | .NET serializes the request body once and creates fresh HTTP messages from those captured bytes. | A caller-mutation regression failed before the fix and now proves the two attempts contain identical original text. |

## Compatibility, reviewed boundaries, and release order

- Existing send/reply/forward calls remain usable. Go adds WithOptions methods;
  Rust adds keyed methods and error accessors without changing ApiError struct
  fields; Java adds overloads; .NET uses distinctly named keyed methods to avoid
  ambiguity with existing cancellation-token calls. Implementers of the public
  .NET interface must add its new methods when upgrading.
- Retry behavior intentionally changes for partial work and ambiguous 503 writes.
  Integrations must reconcile original IDs instead of resending the entire batch.
  Ordinary rate-limit backoff remains available. The default 30-second timeout
  and two-retry configuration are unchanged.
- Tracking health checks endpoint readiness. It cannot infer a pixel load from
  coupon redemption. Domain DNS, custom-host HTTPS, webhook ingestion and email
  rendering remain server responsibilities; SDKs preserve the supplied content.
- Existing SDK folder/source filters, contact upsert forwarding, campaign cancel
  paths, received-delete paths and webhook verification were reviewed against the
  changed API contracts. Their existing resource/conformance tests pass. No
  duplicate editor or tracking implementation was added to an SDK.
- Verification uses local scripted responses and local HTTP servers, not live
  provider handoffs, production tracking hosts, or customer sends. The local Java
  runtime was JDK 26; all minimum supported runtime/OS combinations were not run.
  A separate slow-body Java probe honored its timeout; .NET has a committed
  regression for the same boundary. No claim of universal inbox rendering or
  guaranteed open detection is made.
- Deploy the corresponding backend fixes, including reply/forward operation keys
  and GET /domains/:id/tracking-health, before releasing the SDK changes. Then
  choose a new coordinated SDK version, bump all coordinates and the CLI’s minimum
  Node SDK dependency, and run the release process. Old servers can return 404 for
  tracking-health and do not provide the new reply/forward deduplication contract.
  No commit, push, tag, registry publish, or production deployment was performed.
